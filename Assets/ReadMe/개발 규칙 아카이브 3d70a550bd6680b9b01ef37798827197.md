## A. ID / 명명 체계

| 규칙 | 내용 |
| --- | --- |
| RegionId | 2자리 숫자 string |
| LocalId | 2자리 숫자 string (지역 내부에서만 고유) |
| NodeId | 4자리 숫자 string = RegionId + LocalId (전역 고유) |
| 딕셔너리 키 원칙 | 노드 관련 데이터는 항상 **NodeId(4자리)** 를 키로 사용. LocalId는 지역 간 충돌 위험이 있어 키로 부적합 |
| 인터랙션 키 | 정수가 아닌 **문자열**(`interactionKey`)로 관리. Ink Knot 이름 조합과 일관성 유지 목적 |

## B. 클래스 계급/접미사 규칙

| 접미사 | 소속 | 역할 |
| --- | --- | --- |
| **Manager** | RootScene | 영속 싱글턴. 로직 담당, 상태는 최소화 (State는 별도 클래스로) |
| **Director** | Additive 씬 (NodeScene, BattleScene 등) | 해당 씬 하나를 총괄. 하위 Controller들을 조율. 씬 로드마다 생성/소멸
(BattleDirector은 예외적으로 싱글턴 패턴 도입) |
| **Controller** | Director 하위 | 씬 내 개별 도메인(UI, 적, 아군 등) 전담 |
| ~~State | — | 순수 데이터 저장소, 가변형 데이터를 저장하는 클래스. |
| ~~Data | — | 순수 데이터 저장소, 불변형 고정 데이터를 저장하는 ScriptableObject. |
- **Manager ↔ Director 통신 원칙**: Director끼리는 서로 직접 통신하지 않는다. 요청은 항상 Manager를 경유. Director는 자신의 존재를 Manager에게 "Push 등록"(Awake/OnDestroy에서 등록·해제)하는 방식으로 알림.
- **Data vs State 접미사**: `Data` = 디자인 타임 고정값(ScriptableObject: CardData, QuestData, NodeData 등). `State` = 런타임 가변값(PartyState, NodeState). 미확정 잔여 항목: `DeckConfiguration`(=`equippedDeck`)은 가변값이므로 `DeckState` 계열로 재검토 필요.

## C. 함수 명명 규칙

| 패턴 | 의미 |
| --- | --- |
| `Should~Trigger(id)` | 순수 판정 함수. 상태 변경 없이 bool만 반환 (예: `ShouldStoryTrigger`) |
| `Try~Trigger(id, out path)` | 판정 + 통과 시 상태 갱신까지 수행하는 실행 진입점 (예: `TryTriggerStoryEvent`) |
| `Check~Conditions()` | 여러 `Should~` 후보를 순회하며 판정하는 상위 절차 (예: `CheckEntryConditions`) |
| `Has~` | 이미 저장된 확정 상태를 조회 (판정이 아닌 단순 조회, 예: `HasActiveEncounter`) |
| Get/Set 접두어 통일 | 형용사형을 짝 맞출 것 (예: `SetNodeDangerLevel` — Get과 동일하게 `Danger` 사용, `Dangerous` 금지) |
| 읽기/쓰기 접근자 형태 규정 |   • 단순 필드 반환(부작용 X) → C#프로퍼티(`=>` 또는 자동 프로퍼티) 허용
  • 계산/조합/lazy-init 등 부작용 O → 반드시 Get~ 메서드 사용
  • 쓰기는 반드시 명시적 메서드사용.
  • Set보다는 행위 기반 이름 우선.(`VisitNode, IncreaseInteraction` 등) |

## D. 이벤트 관리 원칙

1. **이벤트는 파괴되지 않는 주체가 소유한다.** 씬 언로드로 파괴될 수 있는 오브젝트(예: BattleScene 소속 Director)는 이벤트를 직접 소유하지 않는다. RootScene 소속 Manager나 정적 허브가 소유.
2. **얇은 이벤트 허브(`GameEvents`) 사용.** 이벤트 "선언과 Invoke 창구"는 한 곳에 모으되, Invoke를 실제로 호출하는 로직 판단은 각 도메인 코드에 남긴다 (완전 중앙화 대신 절충).
3. **구독/해제 쌍은 람다 대신 이름 있는 핸들러 메서드 사용.** `+= () => {...}` 형태는 해제(`=`)가 불가능해 구독 누적(메모리 누수)을 유발.
4. **코루틴 호스트 원칙**: 씬을 로드/언로드하는 코루틴은 반드시 그 씬에 속하지 않는 오브젝트가 host해야 한다. "요청 주체"와 "코루틴 실행 주체"를 분리할 것 — 요청자는 메서드만 호출하고, 실제 `StartCoroutine`은 항상 SceneFlowManager(RootScene) 내부에서 실행.

## E. RuntimeState / 데이터 계층 원칙

1. **모든 지속 가능한 상태는 RuntimeState를 경유한다.** 다른 Manager(StoryProgressManager 등)는 자체 필드로 진행 데이터를 들고 있지 않고 무상태(stateless)로 유지 — 세이브 시스템이 RuntimeState 하나만 순회해도 전체 복원이 되도록 하기 위함.
2. **Lazy-default 패턴.** 조회 시 값이 없으면 null 대신 기본값을 즉시 생성해 반환 (`GetNodeState`). 존재 유무가 아니라 "손댄 적 있는가"만으로 딕셔너리 엔트리 유무를 결정 — 전체 사전 채움 불필요.
3. **단일 진입점.** 모든 필드는 Get/Set 메서드로만 접근. 직접 필드 조작 금지.
4. **동일 정보 중복 저장 금지.** (예: `currentNodeId` 4자리 필드와 `currentRegionId`+`currentLocalId`를 동시에 저장하지 않음 — 조합값은 항상 계산으로 도출)
5. **세이브 저장 대상 필터링.** 초기 상태(미방문/기본값)인 노드는 세이브 데이터에서 제외해 파일 크기 최소화 — Awake 시 빈 컨테이너 생성 → 로드 시 저장된 것만 채움 → 나머지는 lazy-default가 처리.

## F. Ink 스토리텔링 규칙

| 구분 | 형식 | 예시 |
| --- | --- | --- |
| Knot | `{category}_{id}` (설명은 `//` 주석으로) | `story_013`, `node_0001_shop_intro`, `quest_0007_intro` |
| Stitch | `= {목적어}` | `= first_visit`, `= success` |
| 카테고리 | `story_` (선형 사건), `node_` (노드별 인터랙션), `quest_` (퀘스트) | 접두사로 파일 카테고리와 매칭 |
| 파일 분리 | story/quest는 우선 파일 1개로 시작, 규모 커지면 막 단위 분리. node는 노드 하나당 파일 하나 |  |
| 종료 지시어 | 선택지 말단은 `-> END`로 통일 (`DONE`도 동작은 하나, 의미 명확성 위해 END 권장) |  |
| 태그 파싱 | `#speaker:`, `#sheet:`, `#mood:`, `#layout:` — 파싱은 별도 유틸(`DialogueTagParser`)로 일원화, UIController에 로직 분산 금지 |  |
| 게임 상태 연동 | 선택지 결과로 게임 상태(퀘스트 등)를 바꿔야 하면 Ink External Function(`~ FunctionName(args)` + `BindExternalFunction`) 사용 |  |
| 파일명 vs Knot 이름 | 서로 무관 (Ink는 Knot 이름만으로 탐색). 다만 관례상 파일명과 카테고리를 일치시켜 실수 예방 |  |

## G. 트리거 개념 분류 (기획+개발 공통)

| 트리거 종류 | 판정 방식 | 반복 가능 여부 | 소관 |
| --- | --- | --- | --- |
| StoryTrigger | 순번 일치 판정 (`currentStep + 1`), 완전 선형 | 아니오 (1회성) | StoryProgressManager (RuntimeState 경유) |
| BattleTrigger (인카운터) | 저장된 bool 조회, 판정 로직 없음 | 클리어 시 false 전환, 재발동 안됨 | RuntimeState.NodeState |
| InteractionTrigger | 판정 없음, 클릭=즉시 실행 | 예, 무제한 | RuntimeState.NodeState (카운트만) |
| QuestTrigger | 게임플레이 행동 결과로 완료 판정 (별도 시스템) | 퀘스트 성격에 따라 다름 | RuntimeState.questFlags |
- **스토리 사건 ≠ 메인 퀘스트.** 사건(Story Event)은 순수 대사/컷신 단위(선형 카운터로 관리), 메인 퀘스트는 플레이어 행동 목표 단위(개별 완료 플래그로 관리). 메인 퀘스트 하나가 여러 사건을 감쌀 수 있음 (퀘스트 시작 사건 → 목표 수행 → 완료 사건).

## H. 기획 문서 vs 코드 용어 매핑 (혼용 주의 지점)

| 상황 | 기획 문서 용어 | 코드 용어 | 비고 |
| --- | --- | --- | --- |
| 노드의 방문 여부만 | "노드 상태" (탐사 문서 2.3) | 코드에서는 `NodeState.Visited` (일부) | 코드의 `NodeState`는 방문+위험+인카운터+인터랙션 전체를 포괄하는 **더 넓은 개념**으로 확장 사용 중. 향후 기획 문서 개정 시 "방문 상태"로 좁혀 용어 재일치 권장 |
| 마을/던전 구분 | — | `AreaType` (Village/Dungeon) |  |
| 층수 개념 | "복층 레이어" (마을·던전 공통) | `Floor` (int) | `AreaType`과 별도 축, 이름에 "Layer" 재사용 금지 (혼동 방지) |
| 전투/전환 절차 전체 | "이동", "전환" | **Transition** | 트랜지션은 언로드~페이드~로드 전체 절차 지칭 시에만 사용 |
| 적 존재 여부 | "적이 있는지" | **Encounter/인카운터** | "전투 발생"은 결과 상태 지칭 시에만 사용 |

## I. 프로세스/작업 방법론

1. **수직 슬라이스 우선.** 콘텐츠(스토리·배틀 상세) 양산보다 최소 루프(노드이동→인카운터→배틀진입→승리→복귀→미결트리거 이어짐) 완주를 먼저 검증. 검증된 계약 위에 콘텐츠를 쌓아야 재작업 리스크가 낮음.
2. **결정 유예의 명시적 관리.** 미확정 사항(자료형, 저장 방식 등)은 "지금 결정하지 않아도 나중 비용이 적은 형태"로 설계(예: NodeId를 4자리로 미리 고정해 Split 로직 변경 최소화).
3. **과설계 경계.** 지금 요구사항에 없는 확장(지역별 딕셔너리 분리, NodeData ScriptableObject 등)은 실제 필요 시점까지 하드코딩/단순 구조로 유지.
4. **디버그 검증 방식.** 세이브 시스템 없이, 임시 부트스트랩/핫키(F1 등)로 초기 상태를 강제 주입해 최소 루프를 검증. 세이브/로드는 별도 작업으로 분리.
